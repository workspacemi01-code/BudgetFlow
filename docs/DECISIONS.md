# BudgetFlow — Decisions

The master prompt is the product spec. This file records where we deliberately
changed it, and the product answers given so far. Read it before changing the schema.

## Product answers (2026-09-10)

| Question | Decision |
|---|---|
| Budget transfers between departments/lines | Yes. Stored in `budget_transfers`; take effect only when Finance (owner/admin/finance) approves. Dept managers can request transfers between lines they manage. |
| Overspending | Blocked by default. `organizations.allow_over_budget = true` lets owners/admins (not finance) approve over budget; the transaction is flagged `over_budget`. |
| Brand level | Optional on a budget line. Label is per-org (`organizations.brand_label`: Brand / Project / Cost Center). |
| Billing | Phase 6. Paystack for NGN/Africa, Stripe for international. |
| Framework | Current stable Next.js (App Router), not 14. |
| Supabase | Hosted project (no Docker locally). |

## Changes from the master prompt spec

1. **Normal views, not materialized views.** Materialized views ignore RLS (cross-tenant leak through the API) and go stale. All summaries are `security_invoker` views, always live and tenant-isolated. Revisit with per-org caching only if they get slow.
2. **Membership helper functions instead of `limit 1`.** `private.is_org_member(org_id)` etc. so one user can belong to several orgs (org switcher).
3. **Committed = approved − paid** for `approved` and `partially_paid` transactions. The spec's trigger missed approved-but-unpaid money and stored totals on `budget_lines`.
4. **`membership_departments`** links a dept_manager (or a restricted viewer) to one or more departments.
5. **`budget_periods`** (e.g. FY2026). Department budgets (`department_budgets`) and budget lines belong to a period, so history survives year-end.
6. **`payments` table.** Spent = sum of non-voided payments. Transaction status `approved → partially_paid → paid` is derived from payments and cannot be set by hand.

## Conventions

- Money: `numeric(18,2)`; currency is per org.
- Transaction codes: `TXN-1001…`, per org, generated by trigger (explicit codes are kept, e.g. from imports).
- Transaction workflow: `draft → pending → approved → partially_paid → paid`; `pending → rejected → draft/pending`; `draft/pending/rejected/approved (no payments) → voided` (reason required). Amounts and budget line lock once approved.
- Reversals: `txn_type = 'adjustment'` (finance only, reason required, may be negative).
- Budget check happens **at approval**, with a row lock on the budget line so concurrent approvals can't overspend. The UI should also warn at entry.
- Closed periods (`budget_periods.status = 'closed'`) reject changes from users.
- Receipts: private `receipts` bucket, path `{org_id}/{transaction_id}/{filename}`.
- Requests without a user JWT (service role, SQL editor, seeds, webhooks) skip workflow checks; everything from the app goes through RLS + triggers.
- Supabase Auth must keep **email confirmation on**: invitations are matched on the JWT email.
